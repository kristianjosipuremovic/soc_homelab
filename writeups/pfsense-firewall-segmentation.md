# pfSense in Practice: Routing, Firewalling, and Segment Enforcement in my Homelab

## Part 1: What pfSense is

A firewall is a key feature to implement within your homelab. It is a security system designed to prevent unauthorized access in/out of your computer network. They are often used to enforce authorization within networks. A firewall has many responsibilities, many of which depend on the firewall type (L2, L3, packets). Some of these responsibilities include monitoring network traffic, inspecting data packets, regulating traffic, enforcing rules, and protecting against external threats.

So many firewalls have these capabilities, but one key dimension is missing from their functionality: the network layer. Networking provides routing functionality and allows firewalls to both shape traffic as well as send it on to its destination. This is why many firewalls also function as routers. But what is a router? Routers are networking devices which deliver traffic based on layer 3 addresses.

In my homelab, the firewall I am using, pfSense, also has this added router functionality.

Yet pfSense is not just a firewall. pfSense is actually an entire open source router operating system which can be installed on most commodity hardware. It is often used as a router and firewall software, which we just discussed, yet it also is typically configured as a DHCP server, DNS server, WiFi AP, and VPN server all in the same hardware device. It also allows third party open source package installation, expanding the possible range of security functionality even further with options such as Snort or Squid.

So that is just what pfSense is as an operating system, yet what is it as a routing + firewall software, which is what will be used in my homelab? It is a stateful firewall, allowing for the tracking of active connections in a state table. Since it remembers sessions, it has the capability to automatically allow return traffic without needing an explicit rule for the reply. The state tables stateful firewalls use save source IP, destination IP, ports, and protocols for active flows. pfSense, as a stateful firewall, tracks active connections instead of singular packets to establish a clearer picture of the network flow. It provides more comprehensive information for contextual readings of traffic flow, improving readability for security administrators.

In my homelab, pfSense has its own VM and, as the router, is the gateway for every other VM on the network. Every .1 on every subnet is pfSense. When any VM in the network wants to communicate with a different subnet, it sends a packet to pfSense. pfSense physically connects all the networks together. Since pfSense has to be on five networks at once, it needs five NICs, one plugged into each virtual switch. These NICs correspond to each virtual switch generated by libvirt, yet virtual network setup comes later in the homelab.

## Part 2: How pfSense enforces policy — rule structure, evaluation logic, my homelab firewall rules

We've established that pfSense enforces and manages traffic on each NIC in a network, yet how does it actually enforce firewall policies and rules that you set?

In pfSense software, rules on interface tabs are applied per-interface in the inbound direction. Traffic initiated from hosts connected to the LAN is filtered with LAN interface rules. Traffic initiated from hosts on the internet is filtered with WAN interface rules. Rules are stateful by default, so a state table entry is created when traffic matches an 'allow' rule. Rules consist of the following components: states, protocol, source, port, destination, gateway, queue, schedule, description.

There is an exception which can be applied for more complex configurations — Floating Rules. Floating Rules can act on any interface using the inbound, outbound, or both directions. Having them as an option can reduce the number of required firewall rules in some cases.

So what are the rules applied on? In pfSense, interface groups are a method to place rules on multiple interfaces at the same time, which can simplify rule configurations if similar rules are required on many interfaces in the same way. An example of when they could be used are for a collection of interfaces including all LAN type interfaces, or for a group of VLANs.

Rules have an order to which they are processed. There are 3 main L3 rules, and pfSense has a processing order for them, shown here:

1. Floating Rules
2. Interface Group Rules
3. Interface Rules

This order has some limitations, and can prevent desired rule combinations. If a rule on the group tab matches a connection, the interface rules will not be looked at. It is the same with a floating rule, which if set, prevents the consultation of interface group rules for the same connection.

## Part 3: Designing your own firewall rules

The most important step when setting up pfSense in your homelab is the implementation of these rules and groups established above. Just by looking at an empty topology with its many connections, it can be hard to know where to start. The following questions are what I have asked myself when laying out the initial firewall rules for my homelab.

- **What is the industry-standard starting point for zero-trust architecture?**
  - An implicit deny on every interface. Block all connections at first, then implement allow rules to control traffic.
- **(Per-interface) What do hosts on this subnet need to reach, and why?**
  - SOC-NET needs incident response access to corporate hosts on CORP-NET.
- **Logging — who sends logs where?**
  - CORP-NET sends logs to Security Onion (SOC-NET).
  - OT-NET sends logs to Security Onion (SOC-NET).
- **Management — who administers what?**
  - Security Onion (SOC-NET) web console administers IR.
  - Security Onion (SOC-NET) remote access administers IR.
- **OT traffic — what is talking in the OT segment?**
  - There is intra-subnet communication between ScadaBR and OpenPLC over Modbus, so pfSense doesn't see it.
- **DNS — who needs name resolution?**
  - CORP-NET needs DNS to domain controller.
- **Internet access — who needs it, and for what?**
  - SOC-NET needs web access for updates and threat feeds.
